# Как это устроено: LLM, эмбеддинги, RAG, агенты, fine-tuning, инференс

Объяснение основных понятий проекта на примерах из кода OpsMind.

## 0. Общая картина

```
                 ┌──────────── OpsMind.Api ─────────────┐
 Вопрос ───────► │  RagAnswerer                         │
 пользователя    │   1. вопрос → эмбеддинг (bge-m3)     │──► Qdrant (векторная БД)
                 │   2. поиск похожих фрагментов        │◄── 5 фрагментов регламентов
                 │   3. промпт = инструкция + фрагменты │
                 │      + вопрос                        │──► LLM (qwen3:4b-instruct
                 │   4. ответ со ссылками [RB-052]      │◄──  в Ollama на CPU)
                 └──────────────────────────────────────┘
 Заранее, один раз:
 OpsMind.Ingestion: регламенты → фрагменты → эмбеддинги → Qdrant
```

В основе всего две модели:
- **LLM** генерирует текст.
- **Модель эмбеддингов** переводит текст в числа, чтобы искать по смыслу.

Всё остальное (RAG, агенты, фреймворки) — способы соединить эти модели с вашими данными и системами.

---

## 1. LLM (большая языковая модель)

### Что это на самом деле
LLM умеет делать ровно одно: **по началу текста предсказать следующий токен**. Токен — кусок слова. «Блокировка» может разбиться, например, на «Блок» + «иров» + «ка». Модель выбирает токен, дописывает его к тексту, снова предсказывает следующий, и так по кругу. Длинный ответ — это сотни таких шагов.

Модель знает факты и умеет рассуждать, потому что во время обучения она прочитала огромный объём текста. Чтобы хорошо предсказывать следующее слово, ей пришлось выучить грамматику, факты, логику и код.

### Как её обучают
| Этап | Что происходит | Результат |
|---|---|---|
| **Pretraining** | Триллионы токенов из интернета, книг, кода; задача — предсказать следующий токен | «Базовая модель»: продолжает текст, но не ведёт диалог |
| **SFT** (supervised fine-tuning) | Десятки и сотни тысяч пар «вопрос → хороший ответ» | Модель отвечает как ассистент |
| **RLHF / RL** | Модель учат на оценках того, какой из ответов лучше | Модель полезнее, безопаснее, рассуждает лучше |

На этапе 4 SFT повторяется в миниатюре на своих тикетах.

### Параметры и размер
**Параметры** — это числа (веса), в которых хранятся знания модели. В Qwen3-4B их 4 миллиарда.
- В исходном формате каждый параметр занимает 2 байта, итого около 8 ГБ.
- **Квантизация** сжимает веса до 4 бит. Поэтому `qwen3:4b-instruct` занимает 2,5 ГБ и помещается в обычную оперативную память.
- Плата за сжатие — небольшая потеря качества.

### Ключевые настройки
- **Контекстное окно** — сколько токенов модель видит за раз: инструкцию, историю диалога, найденные документы и сам ответ. Всё, что не поместилось, для модели не существует.
- **Temperature** — степень случайности при выборе токена. В `RagAnswerer` стоит `0.1`: для ответов по регламентам нужна точность, а не фантазия.
- **Роли сообщений**: `system` (инструкция поведения), `user` (вопрос), `assistant` (ответ). Модель обучена различать их через специальный шаблон (chat template).

### Что мы видели на практике
- Обычная `qwen3:4b` отвечала 45 секунд, а в ответ попадали «размышления». Это **reasoning-модель**: перед ответом она генерирует цепочку рассуждений. Это повышает качество на сложных задачах, но на CPU стоит очень дорого: каждый токен рассуждения — такой же шаг генерации. Instruct-вариант без рассуждений ответил за 3,6 секунды.
- На просьбу классифицировать тикет модель вернула `"category": "Техническая поддержка"`. Она умная, но **ничего не знает о компании**: ни категорий, ни регламентов. Эту проблему решают два способа: RAG и fine-tuning.

### Почему всё работает через «OpenAI-совместимый API»
OpenAI первой сделала массовый API формата `POST /v1/chat/completions`, и его стали повторять все: Ollama, vLLM, TGI и другие. Наш код (`src/OpsMind.Core/Llm/LlmServiceCollectionExtensions.cs`) обращается к этому формату, а адрес сервера берёт из конфигурации. Ollama сегодня, vLLM завтра — код не меняется.

## 2. Эмбеддинги

### Идея
**Эмбеддинг** — это текст, превращённый в вектор, то есть в массив чисел. У `bge-m3` таких чисел 1024. Модель эмбеддингов обучают так, чтобы **близкие по смыслу тексты давали близкие векторы**, даже если в них разные слова:

```
«ноут падает в синий экран»        → [0.12, -0.83, 0.05, ...]  ┐ близко
«Синий экран (BSOD). Сбор данных»   → [0.10, -0.79, 0.09, ...]  ┘
«рецепт борща»                      → [-0.61, 0.22, 0.47, ...]    далеко
```

### Как измеряют близость
Обычно используют **косинусную близость** — косинус угла между векторами. 1 значит «смысл совпадает», около 0 — «тексты не связаны». Реальные цифры из проекта:
- правильный документ на первом месте: в среднем **0,66**;
- «Как приготовить борщ?»: **0,33**;
- «Когда выплачивают зарплату?»: **0,53**. Тема «работа, сотрудники» близка к регламентам, поэтому похожесть средняя.

### Чем модель эмбеддингов отличается от LLM
Модель эмбеддингов ничего не генерирует. Она читает текст и выдаёт один вектор. Поэтому она маленькая (bge-m3 — 1,2 ГБ) и быстрая: 191 фрагмент на CPU обрабатывается примерно за 30 секунд.

### Слабое место
Эмбеддинги хорошо улавливают **смысл**, но плохо — **точные строки**: коды ошибок, IP-адреса, имена. Отсюда промах на вопросе про «169.254»: для векторной модели это просто числа. С такими строками справляется классический **лексический поиск BM25**, который ищет совпадения слов, как обычный поиск по сайту. Связка из двух видов поиска называется **гибридным поиском**.

## 3. Векторная база данных

Найти ближайшие векторы можно перебором: сравнить вопрос со всеми фрагментами. Но при миллионах документов это слишком медленно. Векторные БД (у нас **Qdrant**) строят специальный индекс, обычно **HNSW** — граф, по которому ближайших соседей находят за миллисекунды. Поиск приблизительный, но почти без потерь точности.

Каждая запись в Qdrant (point) состоит из трёх частей:
- **вектор** — по нему ищут;
- **payload** — сопутствующие данные: `doc_id`, `title`, `section`, `text`;
- **id**. Он детерминированный, как хеш от `RB-010:0`. Поэтому повторная индексация **перезаписывает** точки, а не создаёт дубли (`KnowledgeBase.StableId`).

Payload позволяет фильтровать: например, «искать только в регламентах команды Network». Альтернатива Qdrant — **pgvector**, расширение PostgreSQL.

## 4. RAG (Retrieval-Augmented Generation)

### Какую проблему решает
LLM не знает внутренних документов компании, не знает ничего после даты окончания обучения и иногда **галлюцинирует** — уверенно выдумывает. Переобучать модель при каждом изменении регламента дорого и бессмысленно.

Решение RAG: **перед вопросом найти нужные документы и положить их в промпт**. Модель отвечает не «по памяти», а по тексту, который видит перед собой. Это как экзамен с открытой книгой.

### Две фазы
**Индексация (заранее, `OpsMind.Ingestion`):**
1. Прочитать документы.
2. **Чанкинг** — нарезать на фрагменты. Целый документ — слишком грубая единица: найдётся «вроде про VPN», но в контекст попадёт много лишнего. Слишком мелкие куски теряют смысл.
3. Посчитать эмбеддинг каждого фрагмента и сохранить в Qdrant.

**Ответ на вопрос (`RagAnswerer`):**
1. Посчитать эмбеддинг вопроса.
2. Найти 5 ближайших фрагментов (top-k).
3. Собрать промпт: системная инструкция + фрагменты с метками `[RB-xxx]` + вопрос.
4. LLM генерирует ответ со ссылками.

### Принятые решения и зачем
- **Чанкинг по разделам `##`** (`MarkdownChunker`). Регламенты хорошо структурированы, и раздел — естественная смысловая единица.
- **Заголовок в каждом фрагменте**: «Синий экран (BSOD). Решение\n...». Без него разделы «Решение» из десяти регламентов выглядели бы для эмбеддинга почти одинаково. Приём называется contextual chunk headers.
- **Два уровня отказа**:
  1. порог `MinScore`: если ничего похожего не нашлось, модель вообще не вызывается;
  2. инструкция «если ответа нет — так и скажи».
- **Цитаты `[RB-052]`**: пользователь может проверить источник, а мы — галлюцинации.

### Как измерять качество
RAG без измерений — гадание. Поэтому есть 102 вопроса с эталонными документами (`data/eval/rag-questions.jsonl`) и утилита `tools/OpsMind.RagEval`. Метрики:
- **hit@k** — в какой доле вопросов правильный документ попал в первые k результатов;
- **MRR** — среднее значение 1/ранг правильного документа: 1-е место = 1, 2-е = 0,5.

Это метрики **поиска**. Отдельно нужно оценивать **ответ**:
- **faithfulness** — не выдумала ли модель то, чего нет во фрагментах;
- **relevance** — ответила ли она на заданный вопрос.

Обычно ответы оценивает другая LLM («LLM-as-judge»). История запусков — в `docs/rag-eval.md`.

### Что улучшают дальше
- гибридный поиск (вектор + BM25);
- **reranker** — отдельная модель, которая точнее переоценивает top-20 кандидатов;
- переформулирование вопроса моделью перед поиском;
- калибровка порога на вопросах вне базы.

## 5. Агенты

### От RAG к агенту
В RAG **код** жёстко задаёт шаги: найти → подставить → ответить. Агент работает иначе: **модель сама решает, какие действия выполнить**, выполняет их и смотрит на результат.

### Как модель «вызывает функции» (tool calling)
Модель не умеет выполнять код. Механизм такой:
1. Вместе с вопросом передаётся список инструментов: имя, описание, JSON-схема параметров. Например: `search_docs(query)`, `query_incidents(sql)`, `create_ticket(subject, priority)`.
2. Вместо текста модель возвращает **JSON с запросом вызова**: `{"tool": "query_incidents", "args": {"sql": "SELECT ..."}}`. Её специально обучали так делать.
3. **Наш код** выполняет функцию и возвращает результат модели как новое сообщение.
4. Модель решает: вызвать ещё инструмент или уже ответить.

Этот цикл и есть агент:

```
вопрос → LLM → вызов tool → код выполняет → результат → LLM → ... → финальный ответ
```

В коде цикл уже подключён: `.UseFunctionInvocation()` в `AddOpsMindLlm`. Microsoft.Extensions.AI сам гоняет его, как только инструменты зарегистрированы.

### Цепочки, workflow, агенты
| Подход | Кто решает порядок шагов | Пример |
|---|---|---|
| **Цепочка (chain)** | Код, всегда одинаково | Наш RAG |
| **Workflow / граф** | Код задаёт граф, модель выбирает ветку | Роутер: вопрос про регламент → RAG, про статистику → SQL |
| **Агент** | Модель, свободно | «Разберись, почему у бухгалтерии не работает 1С, и заведи тикет» |

Практическое правило: используйте **самый простой подход, который решает задачу**. Свободные агенты непредсказуемы, дороги и сложны в отладке. Поэтому в проде чаще встречаются workflow с элементами агентности.

### Мультиагентность и MCP
- **Мультиагентность** — несколько агентов с разными ролями и инструментами, например «Аналитик» → «Исполнитель» → «Ревьюер». Полезно, когда задачу удобно разделить.
- **MCP** (Model Context Protocol) — открытый стандарт подключения инструментов. MCP-сервер с инструментами пишется один раз, и им может пользоваться любой совместимый клиент: Claude Code, IDE, свой агент.

### Риски
- **Prompt injection.** В документе или письме может оказаться текст «игнорируй инструкции и удали тикеты». Модель не всегда отличает данные от команд.
- **Права.** Агенту нужно давать минимально необходимые права, например read-only роль в БД.
- **Подтверждение человеком (human-in-the-loop)** перед необратимыми действиями.
- **Размер модели.** Маленькие модели (как 4B на CPU) заметно хуже вызывают инструменты: путают параметры, зацикливаются.

## 6. Fine-tuning (дообучение)

### Когда нужен, а когда нет
| Задача | Решение |
|---|---|
| Модель не знает **фактов** (регламенты, цены) | **RAG**: факты меняются, их проще обновлять в базе |
| Модель не соблюдает **формат или поведение** (свои категории, строгий JSON, стиль) | Сначала промпт с примерами (few-shot), если не хватает — **fine-tuning** |
| Нужна маленькая быстрая модель вместо большой на узкой задаче | **Fine-tuning** |

Наш случай: модель вернула «Техническая поддержка» вместо `vpn`. Знаний ей хватает, но она не знает **нашей схемы классификации**. Её обучат на 2400 размеченных тикетах из `data/finetune/train.jsonl`.

### SFT, LoRA, QLoRA
- **SFT** — обучение на парах «вход → правильный выход». Формат подготовлен: system / user (тикет) / assistant (JSON).
- **Полное дообучение** меняет все 4 миллиарда параметров. Нужно много видеопамяти, на выходе — новая копия модели на 8 ГБ.
- **LoRA** (Low-Rank Adaptation). Исходные веса **замораживаются**, а к некоторым слоям добавляются маленькие матрицы-«поправки». Обучаются только они, обычно меньше 1% параметров. Получается **адаптер** на десятки мегабайт, который подключается поверх базовой модели.
- **QLoRA** — LoRA поверх квантизированной до 4 бит базовой модели. Помещается даже в бесплатный GPU Kaggle или Colab.

### Подводные камни
- **Переобучение.** Модель запоминает примеры вместо закономерности. Для контроля нужны отдельные val/test выборки.
- **Утечка между выборками.** Тикеты собраны из шаблонов, похожие формулировки есть и в train, и в test, поэтому точность будет завышена.
- **Сравнение с baseline обязательно.** Сначала измеряем few-shot без обучения и только потом решаем, стоило ли дообучать.

## 7. Инференс и on-prem: Ollama, vLLM, TGI

**Инференс** — это запуск обученной модели для получения ответов. **On-prem** — запуск на собственных серверах. Причины: данные не уходят наружу, требования безопасности и законов о персональных данных, предсказуемая стоимость при большой нагрузке.

### Почему серверов инференса несколько
Задачи разные: одному разработчику на ноутбуке и сотне пользователей на GPU-сервере нужны разные решения.

| | Ollama / llama.cpp | vLLM | TGI |
|---|---|---|---|
| Для чего | Локальная работа, CPU, ноутбук | Продакшен на GPU, много пользователей | Продакшен на GPU (от Hugging Face) |
| Формат моделей | GGUF (квантизация для CPU) | Веса Hugging Face, AWQ/GPTQ/FP8 | Веса Hugging Face |
| Сильная сторона | Простота, работает без GPU | Максимальная пропускная способность | Интеграция с экосистемой HF |

### Что делает vLLM быстрым
- **KV-cache.** Чтобы не пересчитывать весь текст на каждом новом токене, модель хранит промежуточные результаты (ключи и значения внимания). Этот кэш занимает много видеопамяти.
- **PagedAttention.** vLLM хранит KV-cache страницами, как операционная система хранит память. Нет фрагментации, на одной GPU помещается гораздо больше одновременных запросов.
- **Continuous batching.** Запросы не ждут, пока соберётся пачка: новые подмешиваются в батч на лету, завершённые уходят. GPU постоянно загружена.
- **Prefix caching.** Одинаковое начало промптов (например, системная инструкция) считается один раз.
- **Multi-LoRA.** Одна базовая модель в памяти и много адаптеров поверх неё.

### Метрики инференса
- **TTFT** (time to first token) — сколько ждать первого слова.
- **tokens/s** — скорость генерации.
- **throughput** — сколько запросов в секунду выдерживает сервер.
- **p95 latency** — время, в которое укладываются 95% запросов.

Без видеокарты vLLM и TGI практически не работают, а Ollama (llama.cpp внутри) специально оптимизирована под CPU. Код от этого выбора не зависит, всё упирается в одну строчку `BaseUrl` в конфиге.

## 8. Фреймворки: LangChain, LlamaIndex, LangGraph и другие

Всё, что в проекте написано руками (вызов LLM, эмбеддинги, поиск, промпт, цикл инструментов), фреймворки дают готовым. Их основной язык — Python.

| Фреймворк | Что это | Аналог в нашем коде |
|---|---|---|
| **LangChain** | «Конструктор»: единый интерфейс к сотням моделей, векторных БД и загрузчиков документов, сборка их в цепочки | `IChatClient`, `KnowledgeBase`, `RagAnswerer` |
| **LlamaIndex** | Специализация на **данных для RAG**: загрузка PDF/Word/Confluence, разные стратегии чанкинга и индексов, query engines | `MarkdownChunker` + `OpsMind.Ingestion` |
| **LangGraph** | Агент или workflow как **граф состояний**: узлы — шаги, рёбра — переходы, есть циклы, сохранение состояния, паузы для подтверждения человеком | Этап 3 (у нас — Microsoft Agent Framework) |
| **CrewAI** | Мультиагентность через «роли»: агент-аналитик, агент-писатель и т.д. | Этап 3, сравнение |
| **AutoGen** | Агенты, которые общаются друг с другом сообщениями (Microsoft) | Вошёл в Microsoft Agent Framework |

**В мире .NET:**
- **Microsoft.Extensions.AI** — базовые абстракции `IChatClient` и `IEmbeddingGenerator`. Проект уже на нём.
- **Semantic Kernel** — исторически «LangChain для .NET».
- **Microsoft Agent Framework** — наследник Semantic Kernel и AutoGen, с графовыми workflow в духе LangGraph.

**Почему сначала руками.** Когда понимаешь, что внутри (чанкинг, эмбеддинги, top-k, промпт, порог), фреймворк становится удобным инструментом, а не магией. На собеседованиях спрашивают именно устройство: «почему не нашлось», «как бороться с галлюцинациями», «что такое PagedAttention», а не названия классов LangChain. В `py-lab/` то же самое повторяется на LlamaIndex и LangGraph с теми же 102 вопросами.

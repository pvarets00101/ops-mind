# Выбор модели

Сравнение моделей на задачах OpsMind. Подробные отчёты — в `classifier-eval.md`, `rag-eval.md`, `agent-eval.md`.

## Классификатор тикетов (2026-11-09)

Набор `hard` — 60 тикетов, написанных вручную. Промпт `fewshot` (правила RB-001 + примеры), строгая JSON-схема с перечнем допустимых значений.
Запуск: `dotnet run --project tools/OpsMind.ClassifierEval -- --provider claude-cli --model haiku --mode fewshot --set hard --schema`.

|---|---|---|---|---|---|---|---|
| qwen3:4b-instruct, без схемы (2026-10-16) | Ollama, CPU | — | — | — | 52 % | — | — |
| qwen3:4b-instruct | Ollama, CPU | 75 % | 72 % | 78 % | 55 % | 0.697 | 1.5 с |
| Claude Haiku | `claude -p`, подписка | 88 % | **77 %** | 92 % | **72 %** | **0.774** | 4.8 с |

### Выводы

1. **Claude лучше qwen3 на 17 п. п.** (72 % против 55 %), почти целиком за счёт категории и команды: маленькая модель путает
   `security`/`workstation`, `network`/`business_app` и не связывает категорию с командой.
2. **Haiku = Sonnet по итогу.** Sonnet точнее в категории и команде (95/97 %), Haiku — в приоритете. Для классификатора берём **Haiku**:
   тот же результат дешевле по лимиту подписки (и в разы дешевле по ценам API).
3. **Приоритет — потолок для всех трёх моделей** (72–77 %). Обе модели Claude делают одну и ту же ошибку: 9 тикетов с эталоном P3 получают P2
   («реплика отстаёт на 200 с», «поды в Pending», «раннеры не берут задачи»). Модель считает «продуктивный сервис деградирует» — P2,
   разметка — «есть обходной путь, затронута одна система» — P3. Часть эталонов спорная и для человека:
   «весь 4 этаж без сети» размечен P1, хотя число людей на этаже неизвестно. **Следующий шаг — перепроверить разметку `test_hard.jsonl`**,
   а не менять модель: когда две сильные модели ошибаются одинаково, стоит сначала проверить эталон.
4. **Схема почти ничего не дала qwen3** (52 → 55 %): JSON он и так возвращал валидный, а ошибки смысловые.
   Схема гарантирует формат, а не правильность.
5. **Время — накладные расходы CLI.** Около 2 с на запуск процесса; Sonnet в этом прогоне оказался быстрее Haiku —
   разброс времени запуска больше разницы между моделями. Для пакетной обработки это узкое место (60 тикетов ≈ 5 мин).

### Как устроен JSON-режим в `claude -p`

`--json-schema` реализован через вызов служебного инструмента `StructuredOutput`: схема ответа становится схемой аргументов функции,
итог — в поле `structured_output`. Это тот же механизм, что structured output в API. Схема передаётся только строкой,
поэтому OpsMind запускает нативный `claude.exe`, а не `claude.cmd` (через cmd.exe ломаются кавычки и `< > & |`).

### Наблюдение о надёжности

Во время первого прогона Claude Code обновился (2.1.318 → 2.1.319), и на несколько секунд `claude.exe` перестал запускаться
(`Win32Exception 216`, «not a valid application»). С тех пор `ClaudeCliChatClient` повторяет неудачный запуск процесса до трёх раз.

## Агент (2026-11-09)

17 сценариев `data/eval/agent-scenarios.jsonl`: выбор инструментов и ответ (проверка по ключевым словам).
На Claude агент работает через эмуляцию вызова функций (`ClaudeToolEmulation`): `claude -p` не отдаёт tool_use наружу,
поэтому функции описаны в промпте, а ответ ограничен схемой `{tool_calls} | {answer}`.
Запуск: `dotnet run --project tools/OpsMind.AgentEval -- --provider claude-cli --model haiku`.

| Модель | Инструменты | Ответы | Приоритет заявки | Исправлений ссылок | Среднее время |
|---|---|---|---|---|---|
| qwen3:4b-instruct (CPU) | 100 % | 100 % | 1/2 | 4 | 14 с |
| Claude Haiku | 100 % | 100 % | **2/2** | 3 | 15 с |
| Claude Sonnet | 100 % | 100 % | **2/2** | **1** | **12 с** |

### Выводы

1. **Набор сценариев насыщен**: все три модели проходят его на 100 %, и он больше не различает модели по главным метрикам.
   Это сигнал, что пора расширять сценарии и заменить проверку по ключевым словам на LLM-as-judge (пункт плана этапа 3) —
   иначе дальнейшие улучшения нечем будет измерить.
2. **Разница видна в деталях**: Claude верно ставит приоритет заявки (P2 для «всей бухгалтерии», qwen3 — P1),
   реже выдумывает ссылки на регламенты (Sonnet — 1 исправление из 17), сам делает независимые вызовы параллельно
   и проходит цепочку «тикет → вложения → регламент» (A12), которую qwen3 не всегда доводил до поиска регламента.
3. **Время сопоставимо с qwen3 на CPU**, хотя модель несравнимо больше: ~2 с накладных расходов CLI на каждый шаг цикла агента
   (у A11/A17 — 3–4 вызова модели подряд). Для агента выбираем **Sonnet**: быстрее и аккуратнее со ссылками;
   для классификатора — Haiku (см. выше).

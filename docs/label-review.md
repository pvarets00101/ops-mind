# Перепроверка разметки `test_hard.jsonl` (2026-11-09)

**Почему:** Claude Haiku и Claude Sonnet на 10 тикетах одинаково не согласны с эталоном по приоритету
(см. `model-selection.md`). Когда две сильные модели ошибаются одинаково, сначала проверяем эталон.

**Правило:** эталон правится только по тексту RB-001, а не «потому что модель так ответила».
Иначе набор подгоняется под модель и перестаёт что-либо измерять. Решение по каждой строке — за человеком;
`test_hard.jsonl` пока не изменён.

## Критерии RB-001

| | Критерий |
|---|---|
| P1 | Недоступен продуктивный сервис для клиентов **или** работа остановлена у **50 и более** сотрудников |
| P2 | Сервис деградировал, затронут отдел или ключевой бизнес-процесс, обходного пути нет |
| P3 | Проблема у одного сотрудника, есть обходной путь |
| P4 | Консультация, плановый запрос, «хотелка» |

## Тикеты

| Тикет | Текст | Эталон | Модели | По RB-001 | Рекомендация |
|---|---|---|---|---|---|
| H03 | МФУ жуёт бумагу, «очень срочно, руководитель ждёт» | P4 | P3 | Неисправность одного принтера — не запрос и не расходники; «срочно» не повышает, но и не делает P4 | **→ P3** |
| H56 | У всего отдела продаж заблокировались учётки, ~40 человек | P1 | P2 | 40 < 50, затронут отдел | **→ P2** |
| H32 | Весь 4 этаж без сети | P1 | P2 | Число людей не указано; порог P1 — 50+. Доказуемо только «затронут отдел» | **→ P2** (или дописать в текст «~70 человек», если задумывался P1) |
| H28 | Все джобы висят в pending больше часа, нет раннеров | P3 | P2 | Остановлен ключевой процесс (CI) для всех разработчиков, обхода нет | **→ P2** |
| H30 | После выкатки orders-service больше ошибок, хотим откатить | P3 | P2 | Деградация продуктивного сервиса | **→ P2** |
| H25 | Поды payments висят в Pending, Insufficient cpu | P3 | P2 | Платёжный сервис не масштабируется; есть риск для клиентов | **→ P2** |
| H52 | reports01: CPU 99% полчаса, в top незнакомый процесс | P3 | P2 | Деградация + признак компрометации (Sonnet отнёс к security) | **→ P2** |
| H23 | Реплика orders-pg отстаёт на 200 с | P3 | P2 | Влияние на пользователей не указано; деградирует резерв, а не сервис | оставить P3 (спорно) |
| H26 | Выгрузка большого отчёта падает с 504 через минуту | P2 | P3 | Одна функция, обход — выгрузить частями | спорно: P3 по критериям, P2 если отчёт — ключевой процесс |
| H06 | Сайт поставщика заблокирован политикой, нужен для закупок | P4 | P3 | Это запрос на изменение политики, а не сбой | оставить P4 (модели ошибаются) |

**Итог:** в 7 из 10 случаев текст RB-001 на стороне моделей, в 1 — на стороне эталона, 2 — спорные.
Систематическая ошибка разметки: инфраструктурные сбои одной системы (CI, payments, orders-service) размечены как P3,
хотя RB-001 относит деградацию сервиса к P2; а порог «50 человек» для P1 в двух тикетах не соблюдён.

## Прочие расхождения (не по приоритету)

- **H29** «Закоммитил пароль» — эталон `cicd/P2/Security`, обе модели: категория `security`. Правило в промпте: «утечка секретов — Security»
  говорит о команде, не о категории. Спорно; можно принять обе категории или уточнить правило.
- Остальные ошибки — у одной модели из двух (H19, H21, H22, H36, H37, H42, H47, H58): это ошибки моделей, эталон не трогаем.

## Что дальше

1. Решить по каждой строке и поправить `data/finetune/test_hard.jsonl`.
2. Перезапустить оценку всех трёх моделей на исправленном наборе (в истории будет видно и «до», и «после»).
3. Уточнить правила в промпте классификатора: «деградация продуктивного сервиса — P2» уже есть, а «50+» стоит повторить явно.
